Agents for Humans / Judge architecture

RackHand: how the agents work together.

Strands connects a coordinating Warehouse Agent with two focused specialists. Each agent uses a limited set of tools, returns results the next step can use, and keeps physical actions inside guarded workflows.

Warehouse Agent

The coordinator: understands the request, chooses a specialist or tool, handles approval, and reports the outcome.

Materials Planner

The parts specialist: reads work context, searches the catalog and stock, and returns required parts and quantities. It never moves bins.

Inventory Auditor

The audit specialist: explains recent checks and history. Physical audit execution is enabled only by trusted server configuration.

3 workflow agents + 2 supporting vision agents. The main three use Bedrock; the Vision Analyst and Vision Judge use Gemini through Strands. Motion is simulated. Production camera/scale integration is implemented; AgentCore deployment and scheduled unattended audits are not claimed.

Example request: “Prepare the parts for the upcoming assembly.”

  1. Understand the task

    Receive the request and decide that a grounded parts list is needed.

    Warehouse Agent · Strands Agent
  2. Find the required parts

    Call materials_planner. The specialist reads work context and searches catalog and stock.

    Materials Planner · Agent.asTool()
  3. Approve preparation

    Use the returned requirements in fulfill_materials_plan. Restricted client execution pauses for approval.

    Warehouse Agent · HumanInTheLoop
  4. Check and return bins

    Guarded workflows retrieve bins, verify contents, let the user take parts, then check and save the remainder on return.

    Server tools · Strands Graph
  5. Report the real outcome

    Use structured tool results and verified bin status to report completion, stock changes, or an issue—not an assumed success.

    Warehouse Agent · tool feedback

The Auditor is consulted when audit explanation or history is needed; it is not a mandatory step in preparation. The exact control-module SIMULATION prompt is a separate scripted shortcut with server-grounded requirements, so it can bypass the Planner.

Example request: “Explain the latest check for bin B5-01.”

  1. Receive the question

    Recognize that this is an audit-context question, not permission to move a bin.

    Warehouse Agent
  2. Ask the audit specialist

    Call inventory_auditor through the same controlled specialist interface.

    Warehouse Agent · Agent.asTool()
  3. Read previous evidence

    Use latest-audit and history tools. MemoryManager also supplies relevant persisted audit context.

    Inventory Auditor · MemoryManager
  4. Explain the result

    Return a typed explanation; the Warehouse Agent presents the check status and reason to the user.

    Inventory Auditor → Warehouse Agent
  5. Separate checking from explaining

    If a physical audit is requested, the Warehouse Agent uses execute_inventory_audit with client approval.

    Optional next action · HumanInTheLoop

Client delegation is read-only. The Auditor's run_inventory_audit tool is available only in trusted internal mode, chosen by server code—not by prompt text.

User action: start analysis of the upcoming enabled work.

  1. Read the working plan

    The plan-analysis service reads enabled work for the selected date.

    User → Analysis service
  2. Resolve all required parts

    Invoke the Materials Planner directly with the read plan. Validate its returned parts and quantities.

    Materials Planner · structured output
  3. Choose which bins to check

    Reuse recent unchanged evidence. Checks at least seven days old, missing, changed, or unresolved need verification.

    Server evidence policy
  4. Verify selected bins

    Run server-selected physical audits, return bins to their original slots, and record uncertain results for the report.

    Trusted audit service · Strands Graph
  5. Show assembly readiness

    Report ready materials, shortages, check reasons, and issues based on accepted evidence.

    Analysis service → browser report

This entry point does not pass through the Warehouse Agent. It also does not require the Inventory Auditor language agent: the service calls the deterministic audit workflow directly.

Demonstration boundaries

User-requested parts preparation

“RackHand, prep the parts for the control module.”

  1. Start with stocked demo bins and approve the preparation workflow.
  2. Check B4-01; correct the scripted mismatch in B3-03; remove the scripted unexpected object in B6-03 and retry.
  3. Take parts, then verify each remainder during return. All three bins must return before the final report.

Upcoming-plan readiness

User starts analysis of the upcoming enabled work.

  1. Read the plan and resolve every requirement against real catalog stock.
  2. Reuse fresh, unchanged verification; check stale or unresolved bins through the audit workflow.
  3. Return checked bins and report ready materials, shortages, and issues with the reason for each check.

Demo disclosure: the explicit three-bin SIMULATION scenario supplies scripted images and inspection results, not live Gemini or physical scale evidence. It exercises workflow sequencing and database updates. The PROD path uses Pi captures and Gemini inspection; gantry motion remains simulated. Neither live hardware availability nor production deployment was verified for this architecture review.

AI proposes. Server workflows decide.

Bedrock chooses tools and Gemini inspects photos. Server policies validate evidence, enforce approval requirements, update trusted counts, and record uncertain checks.

Physical evidence is separate from motion.

Production checks use the Pi camera and scale. Gantry movement is currently simulated. Supported capture demos use local fixtures; no real gantry control is implemented.

Inventory remains authoritative.

PostgreSQL stores stock and durable jobs. Realtime is a wake-up signal, not the source of truth. Photos stay in private Storage, and server credentials are never sent to the browser or Pi.

Current demo boundary: motion is simulated. The exact three-bin SIMULATION scenario also scripts its image and inspection results; it is not proof of live camera, scale, or Gemini verification. The PROD path implements those integrations separately.
